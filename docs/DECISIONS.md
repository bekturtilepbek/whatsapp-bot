# DECISIONS.md — архитектурные решения (ADR)

Формат: контекст → решение → альтернативы → последствия. Решение пересматривается
только при наступлении описанного триггера. «Прошлая версия» — предыдущее воплощение
продукта (whatsapp-web.js, копии кода per bot); проект больше не наш, но его уроки —
основание большинства решений. Архив кода хранится вне репозитория.

---

## ADR-001: Baileys как транспорт WhatsApp

**Статус:** принято · сентябрь 2026

**Контекст.** Прошлая версия жила на `whatsapp-web.js` (headless Chrome + инжект JS):
OOM, таймауты CDP, массовые поломки при обновлениях WhatsApp Web.

**Решение.** Baileys — протокольная реализация multi-device по WebSocket, без браузера.

**Альтернативы.** whatsmeow (Go) — сопоставим по качеству, но чужой язык и pre-1.0;
браузерные (venom/wppconnect/wweb.js) — тот же класс проблем; готовые HTTP-обёртки
(Evolution API/WAHA/GOWA) — чужой чёрный ящик поверх тех же движков; официальный
Cloud API — номер уходит в WABA и перестаёт жить в телефоне (ломает handoff «менеджер
отвечает с телефона») + верификация Meta на каждого SMB-клиента.

**Последствия.** ~50 МБ на сессию вместо ~1.5 ГБ. Библиотека неофициальная — бан-риск
управляется поведением (см. анти-бан в FEATURES §7). Транспорт закрыт интерфейсом
`WhatsAppTransport`; Cloud API остаётся опцией per bot.

## ADR-002: Python для ядра, TypeScript только для gateway

**Статус:** принято

Зрелой Python-реализации протокола WhatsApp не существует, поэтому транспорт — TS.
Всё остальное (90% кода: пайплайн, тулзы, интеграции, api) — Python, основной язык
разработчика. Цена — контракт событий описывается для двух языков: источник истины —
`docs/contracts/events.schema.json`, из него генерируются Pydantic и zod. Решение
обратимо: gateway заменяем, не трогая ядро.

## ADR-003: Redis Streams (шина) + Celery (отложенные задачи)

**Статус:** принято

**Контекст.** Две разные потребности: (а) надёжно доставить входящее сообщение в
обработку — конвейер; (б) выполнить функцию в заданный момент с ретраями — будильник
(follow-up, авто-релиз handoff, шаги кампаний). Брокер (RabbitMQ/Kafka) закрывает
только транспорт — исполнитель поверх него нужен в любом случае.

**Решение.** Конвейер — Redis Streams (`XADD`/`XREADGROUP`/`XACK`, pending-list
гарантирует доставку при падении воркера). Будильник — **Celery** поверх того же
Redis; выбран вместо arq по знакомству с инструментом — оба закрывают задачу одинаково.

**Отклонено.** RabbitMQ: второй stateful-сервис; отложенная доставка — только через
плагин или TTL+DLX-трюк, а у нас она — ядро логики. Kafka: нет отложенной доставки
и per-message ack в принципе; операционно тяжелейший вариант; инструмент для потоков
событий иного масштаба. BullMQ: Node-библиотека, отпала с выбором Python. Postgres
как очередь (SKIP LOCKED): рабочая альтернатива, отклонена, поскольку Redis всё равно
обязателен (дедуп, локи, handoff-state) — Streams достаются бесплатно.

**Паттерн отменяемости.** Отложенная задача при срабатывании перепроверяет условие
(клиент написал → follow-up не нужен → no-op). `revoke` — оптимизация, не гарантия:
с `eta` он ненадёжен при рестартах воркеров.

## ADR-004: Docker Compose, без Kubernetes

**Статус:** принято

1–2 узла, один разработчик, он же эксплуатирует. Налог k8s (control plane,
CNI, ingress, cert-manager, апгрейды) наступает сразу, выгоды (bin-packing десятков
сервисов, автоскейл) — не активируются. Всё в контейнерах, worker stateless,
auth-state в БД → переезд в k3s позже механический. Триггеры пересмотра: >6–8 узлов
или выделенный инфраструктурный человек.

## ADR-005: Мультитенантность вместо копий кода

**Статус:** принято

В прошлой версии бот = папка-копия кода + контейнер; копии разъезжались (фикс есть
у одного бота, у соседнего нет), имена таблиц были захардкожены в SQL. Теперь: один
образ, бот — строка в `bots`, тулзы — `tool_bindings`, промпты — `prompt_versions`,
все данные в одной БД с `bot_id`. Обратная сторона — единый Postgres как точка отказа:
бэкапы, мониторинг, позже реплика.

## ADR-006: Состояние — в Redis и Postgres, не в памяти процессов

**Статус:** принято

Уроки прошлой версии: дедуп-Set рос до OOM, таймеры напоминаний умирали при каждом
деплое, локи залипали навсегда. Теперь: дедуп — Redis SET NX + UNIQUE в БД; таймеры —
Celery eta; локи — Redis с TTL; handoff — Redis + БД; auth-state — Postgres. Рестарт
любого сервиса не теряет данные; воркеры реплицируются; сессии переносимы между узлами.

## ADR-007: Секреты вне репозитория

**Статус:** принято

В архиве прошлой версии в репозитории лежали ключи OpenAI, токен Telegram, пароли БД
и `gcp.json`. Правила: `.env` только на серверах; в CI — GitHub Secrets; архив прошлой версии
(содержит секреты) в репозиторий не попадает ни в каком виде, и ни один ключ из
него не используется в новом проекте.

## ADR-008: Классический pip-toolchain

**Статус:** принято

pip + venv + requirements, общие пакеты `libs/*` через `pip install -e`. uv/poetry
дали бы workspaces и скорость, но команда идёт по знакомому пути; решение нулевой
архитектурной важности, мигрируется в любую сторону за вечер.

## ADR-009: Фронтенд — Next.js 15, минимальный UI

**Статус:** принято

Дизайн кабинета будет переделываться, поэтому сейчас — функциональный минимум без
вложений в визуал. Фреймворк — Next.js 15: уже знаком по прошлым проектам, а будущий
редизайн останется рестайлингом внутри того же фреймворка, тогда как путь через
Jinja+HTMX означал бы позже полный переписыванием фронта. Основной объём React-кода
пишет Claude Code. UI-kit — любой, на минимальном UI выбор не важен. Запасной вариант,
если фронт начнёт тормозить проект: срезать до FastAPI + Jinja + HTMX.
