# FEATURES.md — реестр поведения платформы

Реестр поведения продукта. Каждая фича = поведение, которое обязано работать в новой
платформе. Эталон для V1-фич — код прошлой версии (архив хранится у разработчика вне
репозитория, нужные файлы подкладываются в сессию по запросу): если описание здесь
расходится со старым кодом, прав старый код — он работал у реальных клиентов;
расхождение фиксируем в этом файле.

Легенда статуса:
- `V1` — работало в прошлой версии продукта; эталон поведения — архив старого кода
- `V1-DRIFT` — работало не у всех ботов прошлой версии (копии кода разъехались); переносим объединение, включается флагом per bot
- `PLANNED` — обсуждалось для прошлой версии, внедрено не было
- `DROP` — устарело, не переносим
- `NEW` — не существовало, проектируем с нуля

| 1.3 | Батчинг (debounce) входящих | V1 | `batch_timeout_seconds` (по умолчанию 1с). Механизм молча не работал в проде ни разу с момента сдачи — только автотесты (искусственно эмулировавшие конкурентность через `asyncio.create_task`) видели объединение. Исправлено: каждая запись обрабатывается своей asyncio-задачей вместо последовательного `await` (`services/worker/src/worker/pipeline/consumer.py::run_pipeline_consumer`/`_process_and_ack`) — Redis-примитивы батчинга/дедупа/лока и так рассчитаны на конкурентный доступ нескольких реплик воркера, конкурентность внутри одного процесса не создаёт нового класса гонок. Попутно закрыт смежный баг: раньше необработанное исключение на одной записи обрывало `async for` и теряло/откладывало необработку СЛЕДУЮЩЕЙ записи того же батча чтения — теперь каждая запись изолирована в своей задаче. Живая проверка на docker compose подтвердила: два реальных фото с разницей 50мс дали ОДИН объединённый ответ вместо двух |
| 1.4 | Понимание цитирования (quoted context) | V1 | Сдано (2026-09-16). `resolveQuotedContext` — текст цитаты подмешивается в контент сообщения. Формат `[В ответ на: "{текст}"]\n{сообщение}` подмешивается в трёх местах: `messages.content` (обычный текстовый путь, видно и в текущем ходе, и в истории будущих ходов), caption для vision (`_reply_with_vision`), текст перед документом для PDF (`_reply_with_pdf`). Живая проверка на docker compose: прямая публикация в `wa:in` с `quoted_text` → реальный вызов OpenAI (ключ уже добавлен в `.env`) корректно понял контекст цитаты и вызвал `search_products`, вернув правильный товар; сценарий с цитатой на фото без подписи (`quoted_media_type` без `quoted_text`) — бот верно ответил на "а сколько стоит?", опираясь на историю |
| 1.5 | Чёрный список номеров | V1 | Таблица `blocked_contacts` (было `ignoredNumbers` в памяти + reload endpoint). **Пересмотр (2026-09-21)**: в V1 (проверено по архиву, node-bot2/node-bot3 идентичны) заблокированный номер отбрасывался symметрично с паузой бота — до записи в БД, без единого следа в истории. Решение пользователя: привести к тому же принципу, что уже реализован для паузы бота (1.7) — "принимаем и логируем, не отвечаем", а не к V1. ## 2. Медиа-пайплайн

| # | Фича | Статус | Заметки |
|---|------|--------|---------|
| 2.1 | Изображения → vision-анализ | V1 | Отдельный `image_prompt`. **Ревизия (2026-09-16)**: раньше анализировалось только фото ЛИДЕРА батча — остальные фото той же пачки (или фото, прилетевшее ПОСЛЕ текстового лидера в том же окне debounce) никогда не попадали в vision-вызов, оставаясь в истории `[фото]`-заглушками. Теперь все фото окна батчинга (лидер + фолловеры) собираются через `batching.register_image_arrival`/`pop_batch_images` и уходят ОДНИМ мультимодальным вызовом (`llm.client.complete_with_images`, до `MAX_BATCH_VISION_IMAGES=10` штук) — диспетчеризация в `_reply_with_vision` (`services/worker/src/worker/pipeline/consumer.py`) теперь смотрит на наличие фото ГДЕ-ТО в пачке, а не на тип события-лидера. Живой обнаружен и исправлен смежный архитектурный баг батчинга (см. 1.3) — без него объединение никогда не срабатывало бы в проде |
| 2.2 | Голосовые → транскрипция | V1 | ffmpeg → mp3 → STT. Логика переделывалась: транскрипция запускается промисом параллельно с батчингом. **Сдано (2026-09-16), на модели OpenAI вместо ElevenLabs Scribe v2 из V1** (подтверждено пользователем — кыргызский пока не приоритет, важно, чтобы голосовые вообще обрабатывались; ElevenLabs специально выбирался в V1 из-за проблем автодетекта с кыргызским — Whisper может давать более скромное качество на нём). `worker/pipeline/audio.py::convert_to_mp3` — второе появление `ffmpeg` в проекте (первое — сжатие видео, 4.9), OGG/Opus от WhatsApp перекодируется в mp3 перед `llm.client.transcribe_audio` (`whisper-1`, без ретраев — подтверждено пользователем). **Ключевое отличие от vision/pdf**: транскрипт пишется прямо в `messages.content` вместо плейсхолдера `[голосовое сообщение]`, а не строится отдельным "текущим ходом" — дальше обычный `_reply()` видит его как часть штатной истории без единой правки в самой функции (заодно улучшает просмотр переписки, 6.14 — оператор видит реальный текст, не заглушку). Батчинг нескольких голосовых в одном окне — тот же Redis-механизм, что у фото-батчинга (2.1 ревизия), `batching.py` обобщён до `register_batch_media`/`pop_batch_media` с параметром `kind`, чтобы не дублировать код. Сбой (storage/ffmpeg/STT) на любом голосовом пачки — вся пачка деградирует в общий fallback, без частичной транскрипции. Без отдельной настройки "включить голосовые" per bot — в отличие от `image_prompt`/`pdf_prompt`, транскрипция не нуждается в своём системном промпте. Живая проверка на docker compose: синтетический OGG через `ffmpeg`-собранный образ `worker` → реальный вызов Whisper (пустой транскрипт на чистом тоне — ожидаемо, речи не было) → контент обновился в БД → обычный ответ ушёл клиенту |

| 2.5 | Анализ фото и отправка похожего товара | V1 | vision → embedding → `vectorProductSearch` по pgvector |
