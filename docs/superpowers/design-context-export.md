# WhatsApp Bot Platform — контекст для редизайна кабинета (admin-web)

> Экспорт для передачи другой AI-модели, чтобы независимо попробовать
> сделать дизайн кабинета. Самодостаточный документ — не требует доступа
> к репозиторию.

---

## 1. Что это за продукт

Мультитенантная платформа WhatsApp-ботов для малого и среднего бизнеса
(SMB). Клиент (владелец кафе/магазина/клиники и т.п.) подключает свой
WhatsApp-номер через QR-код, настраивает бота (промпт, каталог товаров,
файлы), и бот дальше сам отвечает покупателям через LLM: консультирует,
отправляет карточки товаров, принимает лиды, а при необходимости передаёт
диалог живому менеджеру и забирает обратно.

Greenfield-проект (не бывший в проде под текущим названием), один
разработчик + Claude Code как основной инструмент разработки. Есть
предыдущее воплощение продукта (другой стек, whatsapp-web.js) — от него
унаследована часть поведенческих требований и один экран-референс дизайна
(ниже, раздел 7).

**Ключевой архитектурный принцип:** один код и одна инсталляция на всех
клиентов. Бот — это строка в базе данных, а не отдельная копия кода/сервер
на клиента (в старой версии продукта каждый клиент был отдельной копией
кода — это создавало массу проблем с рассинхроном фич, отсюда сознательный
уход от этой модели).

**Кабинет (тема этого документа)** — веб-интерфейс, через который:
- владелец платформы видит и администрирует ВСЕХ ботов всех клиентов;
- клиент (владелец бизнеса) видит и настраивает ТОЛЬКО своего бота
  (или нескольких, если их несколько).

## 2. Технологический стек

| Слой | Технология |
|------|-----------|
| Транспорт WhatsApp | Baileys (TypeScript) — протокольная библиотека, без headless-браузера |
| Бэкенд-ядро | Python 3.12, FastAPI, SQLAlchemy 2.0 async, Pydantic v2 |
| БД | PostgreSQL 17 + pgvector (векторный поиск товаров) |
| Шина событий | Redis 7 Streams |
| Отложенные задачи | Celery + Celery beat (тот же Redis) |
| **Фронтенд кабинета** | **Next.js 15, App Router, React 19 Server Components** |
| Стилизация (текущая) | **Tailwind CSS v4** (CSS-first `@theme`, без `tailwind.config.js`) |
| Тесты фронтенда | vitest + @testing-library/react |
| Инфраструктура | Docker Compose, без Kubernetes |

Фронтенд — Next.js 15 с App Router, серверные компоненты по умолчанию,
клиентские — только там, где нужна интерактивность (`"use client"`).
Next.js/React/App Router — **не пересматриваются**, речь идёт только о
визуальном языке и вёрстке внутри этого фреймворка.

## 3. Роли и модель доступа

Двухуровневая модель:
- **Владелец платформы** (`is_platform_owner`) — видит ВСЕХ ботов, весь
  платформенный раздел (дашборд по всем ботам, пользователи, аудит-лог,
  расходы на LLM).
- **Клиент** — видит только своих ботов (может быть привязано несколько),
  не видит платформенный раздел вообще.

Аутентификация — JWT-сессии (30 дней), email+пароль. Нет соцавторизации,
нет multi-factor — простая форма логина.

## 4. Экраны кабинета — полная карта (что должно быть в интерфейсе)

Ниже — все существующие сегодня экраны с их функциональным назначением
(что человек может на них сделать). Это и есть основной ввод для дизайна:
каждый экран нужно спроектировать заново, сохранив функциональность.

### 4.1 Не привязанные к конкретному боту (верхний уровень)

| Экран | Путь | Назначение |
|---|---|---|
| Вход | `/login` | Email + пароль. Единственная страница без сайдбара (человек ещё не авторизован) — по центру экрана. |
| Список ботов | `/bots` | Таблица: имя бота, статус подключения (кружок-индикатор: подключён/подключается/не подключён), номер телефона, бейдж «на паузе» если выключен, ссылка «Открыть». У владельца платформы — кнопка «Создать бота». |
| Создание бота | `/bots/new` | Форма из одного поля (имя) — owner-only. |
| Дашборд (owner-only) | `/dashboard` | Операционное здоровье ВСЕХ ботов сразу: статус подключения + время последней активности, «проблемные боты» (разорвана сессия, ждёт QR, переподключается) отсортированы ВЫШЕ здоровых — это диагностический экран для одного человека, следящего за десятками ботов клиентов. |
| Пользователи (owner-only) | `/users` | Список аккаунтов клиентов + матрица доступов «какой пользователь видит какого бота» (чекбоксы/переключатели, по строке на пользователя, по столбцу на бота — может быть широкая таблица при десятках ботов). Форма создания нового пользователя (email+пароль). |
| Аудит-лог (owner-only) | `/audit-log` | Лог всех мутирующих действий в системе: кто, когда, что изменил, у какого бота. Фильтр по боту. У каждой записи можно развернуть JSON-payload (что именно изменилось). Пагинация «показать ещё». |
| Расходы (owner-only) | `/usage` | Токены и стоимость по OpenAI за период (7/30/90 дней/всё время), таблица по ботам + строка «Итого». Подпись, что это оценка, не биллинговые данные. |

### 4.2 Экран одного бота (`/bots/[id]/*`) — общая рамка + 7 вкладок

Каждый экран бота имеет общую «шапку»: имя бота, индикатор статуса
подключения, номер телефона (если привязан), и горизонтальный ряд вкладок.
Дальше — содержимое конкретной вкладки.

| Вкладка | Путь | Назначение |
|---|---|---|
| **Обзор** | `/bots/[id]` | Если номер НЕ привязан — QR-код для сканирования в WhatsApp (обновляется каждые 5с, т.к. WhatsApp сам ротирует QR каждые ~20с). Если привязан — номер телефона + кнопка «Отключить» (logout сессии). |
| **Промпты** | `/bots/[id]/prompts` | Три независимых редактора текста: основной системный промпт, промпт для анализа фото (vision), промпт для PDF от клиента. У каждого — история версий (кто/когда менял, превью старого текста) с кнопкой «откатить» на любую прошлую версию одним кликом. |
| **Товары** | `/bots/[id]/products` | Таблица товаров (фото/название/цена). Форма создания/редактирования: название (обязательно), цена, артикул, описание, минимум одно фото (обязательно, до нескольких штук, с возможностью удалить лишние), переключатель настроек отображения конкретно этого товара (переопределяет глобальные настройки бота — «всё или ничего», не мержится частично). |
| **Настройки** | `/bots/[id]/settings` | Форма из нескольких смысловых секций: переименование бота; батчинг (сколько ждать перед ответом, если клиент дописывает); хендофф (через сколько минут молчания менеджера бот забирает диалог обратно); напоминания молчащему клиенту (вкл/выкл, задержка, текст); настройки медиа (лимит размера, текст-заглушка на неподдерживаемый тип, реакция эмодзи на входящее медиа вкл/выкл+какой эмодзи); выбор модели LLM (ограниченный список, не свободный текст — риск опечатки); включение/настройка инструментов бота (например, «отправлять лиды в Telegram-группу» — id группы + шаблон текста с плейсхолдерами). |
| **Документы** | `/bots/[id]/documents` | Загрузка произвольных файлов (лимит по размеру), список загруженных (имя, тип), удаление. Бот может отправлять эти файлы клиентам по запросу. |
| **Чёрный список** | `/bots/[id]/blocked-numbers` | Список номеров, которые бот игнорирует. Добавление номера (текстовое поле+кнопка), список с пагинацией «показать ещё», удаление. |
| **Песочница** | `/bots/[id]/sandbox` (owner-only) | Тестовый чат с ботом БЕЗ реального клиента — можно отправить текст, фото, PDF и увидеть, как бот ответит (используя настоящий промпт, каталог, тулзы), не тратя ничего в реальной переписке. Оформлен как имитация настоящего WhatsApp-чата на телефоне (зелёные/белые пузыри с хвостиком, индикатор «печатает…», счётчик токенов под ответом бота) — по прямой просьбе владельца продукта: «хочу видеть реальный аналог чата в мессенджере», не обычную веб-форму. Этот экран **сознательно остаётся в своём собственном визуальном языке** (имитация WhatsApp), не обязан визуально совпадать с остальным кабинетом. |

### 4.3 Существующие в бэкенде, но БЕЗ экрана в кабинете (нужно спроектировать с нуля)

Эти возможности уже работают программно, но человеку их негде посмотреть/
использовать — если редизайн включает и это, вот что нужно:

- **Клиенты бота (CRM)** — список контактов (людей, писавших боту): имя,
  телефон, «температура» (горячий/тёплый/холодный — LLM сам оценивает
  диалог), статус менеджера (кто ведёт: бот/человек), краткое авто-саммари
  диалога от LLM, фильтры по температуре/статусу, пагинация. Возможно,
  редактируемые вручную поля (в старой версии продукта менеджер мог
  править имя/статус клиента прямо в таблице).
- **Просмотр переписки** — история сообщений конкретного клиента с ботом
  (лента сообщений, кто отправил — клиент/бот/менеджер, вложения).
- **Рассылки (кампании)** — отправка сообщения (текст/фото/документ)
  массово по существующим диалогам, с антибан-джиттером между отправками,
  статусами доставки/прочтения, возможностью остановить кампанию на лету,
  выгрузкой результата в Excel. (Пока не в скоупе разработки — но layout
  под это может понадобиться.)

## 5. Сквозные UI-паттерны (что должно быть переиспользуемым)

- **Статус подключения бота** — три состояния: подключён / подключается /
  не подключён. Показывается в списке ботов, на дашборде, в шапке экрана
  конкретного бота. Должен быть визуально одинаковым везде (сигнатурный
  элемент интерфейса) — сейчас это цветная точка с подписью, у «подключён»
  — с анимированным пульсирующим кольцом.
  - **Реальная сложность (важно для дизайна):** на дашборде статус имеет
    больше нюансов, чем просто 3 состояния — есть разница между «ждёт QR»,
    «переподключается» и «разорвана сессия» (авария) — эти три сегодня
    визуально различаются лишь мелкой подписью под обычной 3-состояний
    точкой. Хорошее решение этого нюанса — открытый вопрос дизайна.
- **Toast-уведомления** — результат любого действия (сохранено/ошибка)
  всплывает и само исчезает через несколько секунд, без блочных alert().
  Исключение: живой опрос статуса QR/подключения — это не разовое
  действие, а постоянный фоновый процесс, поэтому у него отдельный
  постоянный инлайн-баннер, а не всплывающий toast (иначе спам).
- **Пустые состояния** — у каждого списка/таблицы есть осмысленная заглушка
  для случая «здесь пока пусто», без кнопки-дубликата действия, если
  элемент добавления уже есть в постоянно видимом месте формы над списком.
- **Опасные действия** (удаление товара, документа) — подтверждение
  (`confirm()` или модалка) только там, где действие необратимо на
  сервере; там, где действие тривиально обратимо (например, снятие номера
  из чёрного списка — можно добавить обратно одной формой), подтверждение
  сознательно не ставится.
- **Таблицы с широким набором столбцов** (например, матрица пользователь×
  бот, если ботов десятки) — должны корректно скроллиться по горизонтали
  на узком экране, не ломая остальную страницу.
- **Формы с несколькими полями** — единообразный визуальный ритм между
  подписью поля и самим полем.

## 6. Текущий (заменяемый) визуальный язык — для контекста, не как ограничение

Кабинет прямо сейчас уже прошёл один полный визуальный редизайн (с
голого, вообще нестилизованного HTML) на собственную небольшую
дизайн-систему. Этот раздел — не то, что нужно сохранить, а честный
снимок «откуда стартуем», чтобы новая модель понимала контраст.

**Общий характер:** сдержанный «SaaS-дашборд» — тёмный левый сайдбар
(232px, фиксированный) + светлая рабочая область. Маленькие радиусы
скругления (6–8px), почти без теней — плоские карточки с тонкой рамкой.

**Цветовые токены** (HEX, светлая тема, единственная реализованная —
тёмная тема не делалась):
```
ink        #1c1b19   (основной текст)
ink-soft   #6f6a62   (второстепенный текст)
ink-faint  #a39c8e   (совсем блёклый — плейсхолдеры)
canvas     #faf9f6   (фон страницы)
surface    #ffffff   (фон карточек)
surface-alt #f1efea  (фон шапки таблиц, чуть контрастнее surface)
border     #e4e0d8
sidebar    #1b1a17   (тёмный фон сайдбара)
sidebar-ink #ede9e2
accent     #3459b4   (основной синий)
accent-hover #274783
accent-soft #e8edf8  (мягкий фон для «активного» состояния/бейджей)
success    #1c8a5e
warning    #b7791f
danger     #c0362c
```

**Шрифты:** IBM Plex Sans (интерфейс) + IBM Plex Mono (числа/технические
значения — телефоны, суммы, даты, mime-типы, статусы «как есть»).

**Сигнатурный элемент:** статус-пульс (три состояния из раздела 5) —
маленькая точка + текст, у «подключён» — анимированное расширяющееся
кольцо (`prefers-reduced-motion` отключает анимацию, оставляя статичную
точку).

**Библиотека переиспользуемых компонентов**, которая сейчас есть:
`Card`, `Table` (обёртка над `<table>`, стилизует шапку/строки/hover через
дочерние селекторы), `Button` (варианты primary/secondary/danger),
`Input`, `Textarea`, `NumberField`, `Select`, `Switch` (тумблер),
`Badge` (для «на паузе», «владелец» и т.п.), `EmptyState`, `PageHeader`
(заголовок страницы + подзаголовок + опциональное действие справа),
`Tabs`/`TabLink` (горизонтальные вкладки бота, с горизонтальным скроллом
на узких экранах).

**Известные слабые места текущего дизайна** (честно, чтобы не повторить):
- Статус-пульс на дашборде теряет часть диагностической информации
  (см. раздел 5) — компромисс между единообразием и полнотой данных не
  идеален.
- Одна широкая матричная таблица (пользователи×боты) может стать очень
  широкой при росте числа ботов — сейчас решается просто горизонтальным
  скроллом контейнера, не более элегантного решения не придумано.
- Тёмная тема не реализована вообще (только светлая).
- Мобильная адаптация — desktop-first, мобильная версия не является
  приоритетом (эта платформа используется владельцем бизнеса с ноутбука/
  компьютера, не как основной рабочий инструмент с телефона).

## 7. Референс дизайна ПРЕДЫДУЩЕЙ версии продукта (другой стек, для вдохновения)

У предыдущего воплощения продукта была своя админка (Python/Jinja-шаблоны
+ Bootstrap 5). Важно: разные экраны там были сделаны в разное время и
визуально разъехались по качеству (частая проблема прошлой версии —
копии кода на клиента расходились и чинились по отдельности). Но один
экран управления ботом получил заметно более продуманный, современный
редизайн, который стоит взять за визуальный ориентир:

**Что в нём хорошо и стоит рассмотреть:**
- Полноценная система CSS-переменных с готовой светлой И тёмной темой
  (`[data-theme="dark"]` селектор) — токены: `--ink`, `--ink-soft`,
  `--line` (граница), `--bg`, `--surface`, `--surface-2`, `--brand`,
  `--brand-soft`, `--ok`/`--ok-soft`, `--danger`/`--danger-soft`,
  `--radius: 12px`, `--shadow: 0 1px 2px rgba(20,30,50,.04)`.
  Пример конкретных значений (синий акцент, не такой сдержанный, как
  текущий):
  ```
  светлая: --ink:#1d2433 --ink-soft:#5a6478 --line:#e7eaf0
           --bg:#f7f8fb --surface:#fff --surface-2:#f1f3f8
           --brand:#3b5bdb --brand-soft:#edf0fd
           --ok:#1c8c4a --ok-soft:#e6f5ec
           --danger:#d12c3c --danger-soft:#fdecee
  тёмная:  --ink:#e6edf3 --ink-soft:#9aa6b5 --line:#26303d
           --bg:#0f1419 --surface:#161c24 --surface-2:#1c2430
           --brand:#5b7cf5 --brand-soft:#1e2740
           --ok:#3ddc84 --ok-soft:#15301f
           --danger:#f0506e --danger-soft:#2a1620
  ```
- Шрифт Inter, `font-variant-numeric: tabular-nums` для всех чисел (чтобы
  цифры в таблицах не «прыгали» по ширине).
- Сайдбар 272px с логотипом-плашкой (квадрат с закруглением, залитый
  брендовым цветом, инициал/иконка внутри, белый текст) + название рядом;
  кнопка переключения темы справа в шапке сайдбара; «чип» статуса бота
  прямо под лого (зелёный/красный фон, точка + подпись); пункты навигации
  с мягкой заливкой `--brand-soft` для активного пункта.
- Карточки (`.panel`): рамка + очень мягкая тень + радиус 12px.
- «stat»-блоки: большая цифра (1.9rem, жирная, отрицательный
  letter-spacing) + мелкая серая подпись под ней — компактные плитки
  метрик.
- Пилюли статуса (`.pill`): скруглённые бейджи с мягким фоном под цвет
  статуса (зелёный/красный soft-фон).
- Инпуты: рамка `--line`, при фокусе — рамка `--brand` + мягкое
  свечение `box-shadow: 0 0 0 3px var(--brand-soft)` (кольцо фокуса тем
  же мягким тоном, что и активный пункт навигации — целостность).
- Кнопки: сплошная заливка для основного действия, `ghost` (прозрачная,
  тонкая рамка) для второстепенного, `danger-ghost` (прозрачная с
  красной рамкой/текстом, инвертируется в заливку при hover) для
  опасного — с лёгким `scale(.97)` на `:active` (тактильный отклик).
- Мобильная адаптация в этом экране сделана полноценно: сайдбар уезжает
  за экран и выезжает по кнопке-гамбургеру как оверлей с затемнением
  фона (scrim), появляется отдельный компактный mobilebar сверху.
- Уважение `prefers-reduced-motion: reduce` — отключает все transition/
  animation.

**Экран логина** прошлой версии — простая карточка по центру серого фона,
с тенью и скруглением, иконка WhatsApp сверху, заголовок, подзаголовок,
два поля, кнопка на всю ширину карточки — концептуально то же самое
решение, что и в текущей версии, просто на голом Bootstrap вместо
кастомных токенов.

**Экран переписки/чата** (тестовый чат с ботом внутри админки, предок
нынешней «Песочницы») — пузыри сообщений с намёком на «хвостик»:
пользовательские — зеленоватый фон с закруглением 12px кроме одного угла
(имитация мессенджера), ответы бота — белый фон с рамкой, аналогично
скруглённые с обратной стороны; таймстемп мелким серым текстом под
пузырём. Это уже почти один в один перенесено в нынешнюю Песочницу.

**Чего в старой версии делать НЕ стоит** (антипаттерны, найденные при
осмотре других экранов того же продукта): голая таблица Bootstrap
(`table-dark`, `table-striped`, `table-hover` без кастомизации) для
списка клиентов — плоско, без вышеописанной системы токенов, читается
хуже, чем остальной продукт; редактирование ячейки таблицы через
клик-по-тексту-открывает-скрытую-форму-под-строкой — рабочий, но не
элегантный паттерн инлайн-редактирования.

## 8. Что сознательно НЕ является предметом редизайна

- Бизнес-логика, API-контракты, серверный код — не трогаются, речь
  строго про визуальный слой и вёрстку внутри Next.js/React.
- `SandboxChat` (вкладка «Песочница») — уже сознательно имитирует
  WhatsApp-интерфейс по прямому запросу владельца продукта, не обязан
  подчиняться общему визуальному языку кабинета.
- Тёмная тема — сейчас не приоритет (но раз в референсе прошлой версии
  она реализована элегантно через CSS-переменные — заложить архитектуру
  токенов так, чтобы тёмная тема была дешёвой в будущем, приветствуется).
- Публичный домен/деплой/HTTPS — вне скоупа дизайна интерфейса.

## 9. Формат желаемого результата

Визуальный макет/дизайн-система (не обязательно рабочий код) минимум
следующих экранов, которые лучше всего показывают палитру задач:
1. Вход (`/login`)
2. Список ботов (`/bots`) — включая состояние с пустым списком
3. Дашборд владельца платформы (`/dashboard`) — экран с самой сложной
   информационной плотностью (много ботов, разные статусы)
4. Один бот → вкладка «Обзор» — оба состояния (ждёт QR / подключён)
5. Один бот → вкладка «Настройки» — форма с несколькими секциями
6. Один бот → вкладка «Товары» — таблица + форма создания/редактирования
   с загрузкой нескольких фото

Плюс — предложение по сигнатурному элементу статуса подключения (см.
раздел 5, известная нерешённая проблема текущего дизайна) и по общей
цветовой/шрифтовой системе (токены, готовые расширяться на тёмную тему).
