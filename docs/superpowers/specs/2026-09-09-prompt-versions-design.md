# Промпты с версиями (Волна 3, второй под-проект) — дизайн

**Статус:** approved · 2026-09-09
**Фичи FEATURES.md:** 6.6 (редактирование промптов), 3.7 (дата изменения), 3.8 (версионирование с откатом)

## Контекст

Волна 3 разбита на упорядоченные под-проекты (первый — QR-экран, сдан). Это
второй. По решению пользователя 3.7/3.8 (история + откат) объединены с 6.6
(сам редактор промптов, которого в admin-web пока нет) в один экран — без
редактора версии негде было бы сохранять.

На момент дизайна `bots.system_prompt`/`image_prompt`/`pdf_prompt` — обычные
колонки без истории: `PATCH /bots/{id}` (уже реализован, Блок 3 STAGE1_CORE)
их просто перезаписывает. Таблицы `prompt_versions`, упомянутой в
`docs/ARCHITECTURE.md` §5, не существует — миграции не было.

## Явно отложено на потом (не в скоупе этой итерации)

- **6.18 роли/авторизация** — `author` в `prompt_versions` заполняется
  статичной строкой `"admin"`; станет осмысленным при 6.18.
- **6.19 аудит-лог** — по этой же причине не делаем отдельный `POST
  .../rollback`: откат сейчас неотличим от обычного редактирования на
  уровне API (оба идут через `PATCH /bots/{id}`), различать их как разные
  типы действий понадобится только вместе с аудит-логом.
- Технический долг Волны 3 (QR-экран): dev-сервер Next.js в проде,
  отсутствие `.dockerignore` у admin-web, гонка `refresh()`/сообщения об
  ошибке в `QrPanel` — не трогаем, вне скоупа этого под-проекта.
- Известная, не новая для этой итерации особенность `PATCH /bots/{id}`:
  `image_prompt`/`pdf_prompt` можно перевести из NULL в строку и обратно
  в другую строку, но нельзя явно очистить обратно в NULL (`None` в
  `BotPatch` неотличим от «поле не передано» на уровне `update_bot`). Не
  чиним — не в скоупе версионирования, будет отдельной находкой при
  желании.

## Архитектура

- **Источник истины для «текущего» промпта** — как и сейчас, колонки
  `bots.system_prompt`/`image_prompt`/`pdf_prompt`. `prompt_versions` —
  **только история**, ничего в worker (который читает эти колонки для
  LLM-контекста) не меняется и не рискует.
- **Запись версии происходит внутри `update_bot`** (`libs/db/src/db/bots.py`)
  — не новым write-эндпоинтом. Когда PATCH меняет `system_prompt`/
  `image_prompt`/`pdf_prompt`, `update_bot` сравнивает новое значение с
  последней версией этого `kind` в `prompt_versions`; совпадает — не
  пишет (no-op PATCH не плодит дубли); отличается — добавляет строку.
- **Откат = обычный PATCH со старым текстом.** Единственный новый
  API-эндпоинт — чтение истории: `GET /bots/{id}/prompts/{kind}/versions`.
  Кнопка «Откатить» в admin-web берёт `body` нужной версии из уже
  полученного списка и шлёт его обычным `PATCH /bots/{id}` — новая
  версия-ревёрт создаётся тем же общим механизмом сравнения. Явное
  решение пользователя: не заводить `POST .../rollback` сейчас.
- **Откат не стирает историю** (как `git revert`, не `git reset`) —
  откат добавляет новую версию поверх, старые версии остаются читаемыми.

## Данные

Новая таблица `prompt_versions` (Alembic-миграция):

```
prompt_versions
  id          UUID PK, gen_random_uuid()
  bot_id      UUID FK -> bots.id ON DELETE CASCADE, NOT NULL
  kind        String, NOT NULL   -- "main" | "image" | "pdf"
  body        Text, NULL          -- см. ниже про NULL-семантику
  author      String, NOT NULL, default 'admin'
  created_at  DateTime(tz), NOT NULL, default now()

  INDEX (bot_id, kind, created_at)  -- под list_versions
```

`kind` — обычная строка (как `Message.role`, `ToolBinding.tool_name` в этом
проекте), не Postgres ENUM — миграции на добавление нового kind проще.
Без `relationship` на `Bot` — история читается только напрямую по
`bot_id`+`kind`, лишний eager-load не нужен (учтён урок QR-экрана:
`get_bot`/`get_bot_with_session`).

**NULL-семантика при сравнении «изменилось ли»:** запрос последней версии
делает `.first()` (Row-объект или `None`), а не `.scalar_one_or_none()` —
это различает «версий ещё не было вообще» (`None`, первая запись всегда
считается изменением) от «последняя версия была с `body=NULL`» (`Row(body=None)`,
сравнение `row.body != new_body` работает корректно). Без этого разделения
первое сохранение image/pdf-промпта либо всегда считалось бы «без
изменений», либо ошибочно писалось бы дважды.

Поскольку `image_prompt`/`pdf_prompt` через существующий `PATCH` можно
только выставить из NULL в строку (не наоборот — см. «Отложено» выше),
версия пишется только когда `update_bot` получает не-`None` новое
значение для kind — то есть ровно то же условие, что уже решает,
попадёт ли поле в UPDATE `bots`.

## API

Единственный новый роут:

```
GET /bots/{bot_id}/prompts/{kind}/versions -> list[PromptVersionOut]
```

`kind: Literal["main", "image", "pdf"]` — невалидное значение возвращает
422 силами FastAPI/Pydantic. Список — новые сверху (`ORDER BY created_at DESC`).
`PromptVersionOut = {id, body, author, created_at}` (`kind`/`bot_id`
избыточны в ответе — уже в URL).

`PATCH /bots/{bot_id}` не меняет свою внешнюю схему — `BotPatch`/`BotOut`
как есть; версионирование целиком внутри `update_bot`, невидимо для
вызывающего кроме побочного эффекта в БД.

## admin-web

- Новая страница `app/bots/[id]/prompts/page.tsx` (Server Component,
  SSR-фетч бота + все три списка версий параллельно). Ссылка на неё — с
  `/bots/[id]` (QR-экран, не переделываем), и обратная ссылка со страницы
  промптов.
- Три секции на странице — main/image/pdf — каждая: заголовок,
  `<textarea>` с текущим значением, кнопка «Сохранить» → `PATCH`; ниже —
  список версий (дата, автор, укороченный превью текста) с кнопкой
  «Откатить» на каждой строке.
- `lib/api.ts`: `Bot` расширяется полями `system_prompt: string`,
  `image_prompt: string | null`, `pdf_prompt: string | null` (уже есть в
  `BotOut` на бэкенде, просто не были нужны admin-web раньше). Новые
  функции: `patchBotPrompt(baseUrl, botId, field, value) -> Promise<Bot>`
  (тонкая обёртка над `PATCH /bots/{id}`) и
  `fetchPromptVersions(baseUrl, botId, kind) -> Promise<PromptVersion[]>`.
- Без Tailwind, тот же обычный CSS, что и на QR-экране (ADR-009).

## Живая проверка (конец итерации)

На уже поднятом dev-стеке: открыть `/bots/[id]/prompts` для существующего
бота, изменить основной промпт, сохранить, увидеть новую версию в списке;
сохранить второй раз без изменений — версия не задублировалась; откатить
на первую версию — текст в textarea и `bots.system_prompt` вернулись к
исходному, при этом в списке версий появилась новая (третья) запись, а не
удалились предыдущие две.
