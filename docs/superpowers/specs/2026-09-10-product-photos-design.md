# Товары: загрузка фото (Волна 3, пятый под-проект) — дизайн

**Статус:** approved · 2026-09-10
**Фичи FEATURES.md:** 6.8 (CRUD товаров + обязательные/необязательные поля) —
вторая, завершающая половина; попутно закрывает часть 4.3 (ресайз перед
отправкой карточки, был сознательно отложен в Волне 2 из-за отсутствия
upload-пайплайна для изображений)

## Контекст

Первый под-проект 6.8 (`2026-09-10-product-crud-design.md`, уже в `dev`)
сдал CRUD текстовых полей товара и явно отложил обязательность фото —
в проекте вообще не было write-пути для медиа со стороны Python
(`libs/integrations/src/integrations/storage/` умел только `get()`).
Схема `product_images` существует с Волны 2 (миграция уже применена),
не используется для записи.

Этот под-проект закрывает 6.8 целиком: `Storage.put()` (Python-сторона,
симметрично уже существующему TS `put()` в `services/gateway/src/storage/`),
обязательность `name`+фото при создании товара, управление фото
существующего товара (добавить/удалить, без переупорядочивания), ресайз
перед сохранением (закрывает отложенный пункт 4.3).

## Явно отложено на потом (не в скоупе этой итерации)

- **Переупорядочивание фото (drag/кнопки вверх-вниз).** Решение
  пользователя — добавить + удалить, без реордера. `position` при
  добавлении — просто следующий свободный по порядку.
- **Товары без фото, созданные до этого под-проекта** (первая половина 6.8,
  уже в `dev`) — требование НЕ ретроактивно. Такие товары продолжают
  существовать без единой фотографии: текстовый `PATCH` для них работает
  как раньше, `DELETE`-последнего-фото не применяется (у них и так ноль),
  «Добавить фото» доступно всегда, до достижения лимита в 10. Никакой
  миграции/бэкфилла не делаем.
- **Явная очистка `price`/`sku`/`description` в NULL через `PATCH`** —
  тот же принятый паттерн из первого под-проекта, не пересматривается
  здесь.
- **Прямые публичные ссылки на S3/DO Spaces** — не делаем. Всё фото
  отдаётся через api (`GET .../photos/{photo_id}`), не напрямую из
  хранилища — не нужно городить bucket-policy/presigned URLs сейчас, и
  этот эндпоинт — естественная точка для авторизации, когда придёт 6.18
  (роли и доступы).
- **Конвертация формата при ресайзе** (например, всё в WebP) — не делаем,
  только уменьшение размеров, формат сохраняется как загружен.
- **Клиентская валидация и превью в `ProductForm`** (раздел admin-web выше
  планировал дублирование серверных проверок — 1–10 файлов, ≤10 МБ каждый,
  допустимый MIME-тип — и превью выбранных фото через `URL.createObjectURL`)
  — не реализовано в этой итерации (найдено финальным ревью, 2026-09-10).
  Сейчас в `ProductForm` есть только проверка «выбран хотя бы один файл»;
  все остальные ограничения проверяет только сервер — невалидный выбор
  стоит лишнего round-trip'а вместо мгновенной ошибки, но не пропускает
  ничего недопустимого (сервер — единственная точка принуждения). Осознанный
  пробел, не забыто — доделывается отдельной итерацией UI, не в этом фикс-раунде.

## Архитектура

### Storage.put()

Симметрично уже существующему TS-интерфейсу (`services/gateway/src/storage/types.ts`):

```python
class Storage(Protocol):
    async def get(self, key: str) -> bytes: ...
    async def put(self, key: str, data: bytes, mime_type: str) -> None: ...
```

`FilesystemStorage.put` — `mkdir(parents=True, exist_ok=True)` (родительской
директории для ключа может не быть) + запись файла; та же защита от path
traversal, что уже есть у `get()` (резолвим оба пути, проверяем
`is_relative_to`). `S3Storage.put` — `put_object(Bucket=..., Key=key,
Body=data, ContentType=mime_type)` через `asyncio.to_thread`, тот же
`Config(connect_timeout=10, read_timeout=20)`, что уже используется в
`get()` (CLAUDE.md: «любой внешний вызов — с таймаутом»).

Ключ объекта: `bots/{bot_id}/products/{product_id}/{photo_id}` (`photo_id`
= `ProductImage.id`, UUID). `position` НЕ входит в ключ — она живёт только
в БД, чтобы будущая смена позиции (если появится) не требовала
переименования объекта в Storage.

### Создание товара — один multipart-запрос, всё или ничего

`POST /bots/{bot_id}/products` меняется с JSON на `multipart/form-data`:
`name`/`price?`/`sku?`/`description?`/`display_custom?` — form-поля (те же
типы, что и раньше, просто в текстовом виде — form-data не знает JSON-типов;
`display_custom`, если передан, — JSON-строка, парсится и валидируется как
`dict[str, Any]`), `photos` — 1..10 файлов, **обязательно** хотя бы один.

Порядок на бэкенде:
1. Валидация файлов: количество (1–10), тип (`image/jpeg`|`image/png`|`image/webp`),
   размер (≤10 МБ каждый) — до любой записи в БД. Это не тот же случай, что
   «лимит ДО скачивания» из CLAUDE.md (входящее медиа от анонимного
   отправителя по WhatsApp) — здесь загружает авторизованный админ через
   свой браузер, `UploadFile` в FastAPI сам спулит тело на диск при
   превышении небольшого порога в памяти; проверка размера — всё равно
   первым делом после получения файла, до ресайза/записи в Storage, но не
   препятствует самому приёму тела запроса на транспортном уровне (это не
   входит в скоуп — при желании ограничивается отдельно на уровне
   uvicorn/nginx `client_max_body_size`).
2. Валидация `name` (непустая строка после `.strip()`).
3. Проверка существования бота (404, как и раньше, до insert — тот же
   принцип, что уже был в первом под-проекте).
4. `INSERT` товара (`flush`, не `commit`).
5. Для каждого файла: `Image.open()` (Pillow) — это ЖЕ и валидация
   декодируемости (битый/поддельный файл упадёт здесь → 422, не мусор в
   Storage), ресайз до ~1280px по длинной стороне (формат не меняется),
   `Storage.put()`, `INSERT product_images`.
6. Один `commit` товара + всех фото вместе.
7. Если что-то на шагах 1–6 падает — откат транзакции БД: товар не
   создаётся (ни он сам, ни `product_images`). Уже успевшие улететь в
   Storage файлы (если сбой случился не на первом фото) НЕ удаляются —
   `Storage` в этом проекте умеет только `get`/`put`, `delete` не входит в
   скоуп этого под-проекта (YAGNI: путь редкий — сбой ровно между двумя
   `put()` в рамках одного запроса, — остаются осиротевшие объекты в
   Storage, не БД-строки; принято сознательно, не течёт наружу как баг для
   пользователя).

Расчёт эмбеддинга (как в первом под-проекте — синхронная попытка +
Celery-подстраховка при сбое) идёт ПОСЛЕ этого коммита, отдельной
транзакцией — не меняется, фото на эмбеддинг не влияют (он всё ещё только
из `name`+`description`).

### Управление фото существующего товара

Два новых эндпоинта, независимых от текстового `PATCH` (тот остаётся
JSON-only, фото не трогает):

- `POST /bots/{bot_id}/products/{product_id}/photos` — multipart, 1+ файлов,
  те же валидация/ресайз/лимиты, что при создании; лимит 10 считается
  суммарно с уже существующими фото товара. `position` нового фото —
  `max(существующие position) + 1` (или `0`, если фото ещё не было).
- `DELETE /bots/{bot_id}/products/{product_id}/photos/{photo_id}` — 204;
  422, если это последнее фото товара (обязательность не даёт снести все
  фото до нуля); 404, если фото не найдено в скоупе
  `bot_id`+`product_id`+`photo_id` вместе (тот же принцип "чужое — не
  существует", что уже применяется для товаров).

### Отдача фото в браузер

`Storage.get()` сейчас читает байты только внутри Python-процесса (worker),
наружу не отдаёт. Новый эндпоинт:

```
GET /bots/{bot_id}/products/{product_id}/photos/{photo_id}
```

Стримит байты как есть, `Content-Type` = сохранённый `mime_type`, 404 вне
скоупа. admin-web использует URL этого эндпоинта прямо в `<img src>`.

## Данные

Схема не меняется — `product_images` уже полная с Волны 2. Добавляется
`relationship` на `Product` к `ProductImage` (`lazy="selectin"`,
`order_by=ProductImage.position`) — чтобы `GET /bots/{bot_id}/products`
(список) не ловил N+1 при отдаче миниатюр: `selectin` даёт один
батч-запрос на страницу вместо запроса на товар.

`libs/integrations/src/integrations/storage/`:
- `FilesystemStorage.put(key, data, mime_type)`
- `S3Storage.put(key, data, mime_type)`

Новая зависимость `libs/integrations`: `Pillow` (ресайз). Новая зависимость
`services/api`: `python-multipart` (FastAPI требует его для парсинга
`UploadFile`/form-data, сейчас в проекте нигде не используется — это первый
multipart-эндпоинт в api).

## API

```
POST   /bots/{bot_id}/products
       multipart: name, price?, sku?, description?, display_custom?,
       photos (1..10 файлов, обязательно)
       -> ProductOut, 201 | 422 (валидация) | 404 (бот не найден)

PATCH  /bots/{bot_id}/products/{product_id}
       JSON, без изменений — фото не трогает

POST   /bots/{bot_id}/products/{product_id}/photos
       multipart: photos (1+ файлов, суммарно ≤10 с уже существующими)
       -> list[ProductPhotoOut], 201 | 422 | 404

DELETE /bots/{bot_id}/products/{product_id}/photos/{photo_id}
       204 | 404 (вне скоупа) | 422 (последнее фото товара)

GET    /bots/{bot_id}/products/{product_id}/photos/{photo_id}
       стримит байты, Content-Type = mime_type, 404 вне скоупа
```

Схемы (`services/api/src/api/schemas/products.py`):

```python
class ProductPhotoOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: UUID
    position: int

class ProductOut(BaseModel):
    ...  # существующие поля без изменений
    photos: list[ProductPhotoOut]
```

`ProductCreate` (JSON-схема) уходит из `POST` (теперь multipart, поля
парсятся через `Form(...)`/`File(...)` параметры роута, не Pydantic-модель
тела запроса) — `ProductPatch` для `PATCH` не меняется.

## admin-web

- **`ProductForm`, создание** — поле фото обязательно:
  `<input type="file" multiple accept="image/jpeg,image/png,image/webp">`,
  превью выбранных файлов через `URL.createObjectURL` (без сети).
  Клиентская валидация дублирует серверную (1–10 файлов, ≤10 МБ каждый,
  допустимый тип) — быстрая обратная связь до сабмита. Сабмит собирает
  `FormData`, `createProduct(baseUrl, botId, input, photos)` — сигнатура
  меняется, теперь multipart.
- **`ProductForm`, редактирование** — отдельная секция «Фото» под
  текстовыми полями, независимая от кнопки «Сохранить» тех полей: сетка
  миниатюр (`<img src>` на `GET .../photos/{photo_id}`), «Удалить» на
  каждой (задизейблена, если фото ровно одно), `<input type="file"
  multiple>` «Добавить ещё» — сразу шлёт на `POST .../photos`.
- **`ProductsTable`** — колонка миниатюры (`photos[0]`), пусто/плейсхолдер
  для товаров без фото (созданных до этого под-проекта).
- Без Tailwind, обычный CSS (ADR-009), как и весь остальной кабинет.

## Живая проверка (конец итерации)

На поднятом dev-стеке: создать товар с двумя фото — оба видны в
миниатюрах, размеры файлов в Storage меньше исходных (ресайз применился);
попробовать создать товар без фото — форма не даёт отправить; добавить
третье фото существующему товару; удалить одно — осталось два, кнопка
«Удалить» доступна; удалить второе — осталось одно, кнопка «Удалить»
задизейблена, прямой DELETE-запрос (curl) на последнее фото отдаёт 422.
